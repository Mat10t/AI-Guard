# Требования к MVP проекта единого LLM-шлюза

## 1. Business Requirements

### BR.1: Быстрый самостоятельный старт организации

**Цель:**
- Обеспечить организации возможность самостоятельно зарегистрироваться, получить доступ и перейти к первой интеграции.

**Описание:**
- Продукт должен позволять начать работу без обязательного ручного сопровождения на этапах регистрации, создания проекта и получения параметров интеграции.

**Критерии приемки:**
- Организация может пройти путь от регистрации до первого тестового запроса в рамках одного сервиса.
- Для начала работы достаточно создать организацию, проект и ключ интеграции.

**Исключения и ограничения:**
- Требование не описывает коммерческие условия подключения.
- Требование не фиксирует работу поддержки как обязательную часть сценария.

----

### BR.2: Централизованное управление интеграцией и выбором моделей

**Цель:**
- Дать организации единый способ управлять интеграцией проектов и выбором моделей в рамках одного сервиса.

**Описание:**
- Продукт должен предоставлять единый контур работы с проектами, ключами интеграции и каталогом моделей без необходимости собирать эти возможности в разных внешних системах.

**Критерии приемки:**
- Работа с интеграцией выполняется в контексте проекта.
- Пользователь может получить параметры интеграции и ознакомиться с доступными моделями.

**Исключения и ограничения:**
- Требование не описывает сложные сценарии маршрутизации между моделями.

----

### BR.3: Управляемое использование и контроль расходов

**Цель:**
- Дать организации возможность контролировать использование сервиса и связанные расходы.

**Описание:**
- Продукт должен поддерживать лимиты и предоставлять аналитику и отчетность по использованию.

**Критерии приемки:**
- Организация может ограничивать использование сервиса.
- Организация может просматривать расходы и выгружать отчет.

**Исключения и ограничения:**
- Требование не описывает финансовый документооборот и тарификацию следующего этапа.

----

### BR.4: Ролевое разграничение доступа

**Цель:**
- Обеспечить разделение прав доступа между участниками организации.

**Описание:**
- Продукт должен поддерживать приглашение пользователей и назначение ролей с различным набором прав.

**Критерии приемки:**
- Доступ к функциям системы зависит от роли пользователя.
- Организация может назначать роли участникам.

**Исключения и ограничения:**
- Требование не описывает кастомные роли.

----

### BR.5: Прозрачность технических и управленческих действий

**Цель:**
- Дать организации прозрачность по техническим запросам, административным изменениям и расходам.

**Описание:**
- Продукт должен предоставлять технические логи, аудит изменений, аналитику и экспорт отчетов.

**Критерии приемки:**
- Пользователь с соответствующими правами может разбирать запросы и изменения настроек.
- Пользователь с соответствующими правами может получить аналитические данные и отчет.

**Исключения и ограничения:**
- Требование не фиксирует внешние BI-интеграции.

----

### BR.6: Устойчивость клиентских запросов

**Цель:**
- Снизить риск остановки клиентских сценариев при сбоях отдельных маршрутов обработки запросов.

**Описание:**
- Продукт должен показывать состояние моделей и провайдеров и поддерживать настройки отказоустойчивости на шлюзе.

**Критерии приемки:**
- Пользователь может видеть состояние маршрутов.
- При отказе основного маршрута шлюз применяет предсказуемое поведение.

**Исключения и ограничения:**
- Требование не гарантирует успешное выполнение запроса при недоступности всех допустимых маршрутов.

##### US.1.1_UC.1: Регистрация организации

**Описание:**
- Use Case описывает создание организации и первой учетной записи.

##### Сценарий:
1. Пользователь открывает форму регистрации.
   - Система: Отображает поля для данных организации и первой учетной записи.
2. Пользователь заполняет обязательные поля.
   - Если данные корректны:
     - Кнопка отправки становится доступной.
   - Если данные некорректны:
     - Система показывает сообщение об ошибке.
3. Пользователь отправляет форму.
   - Система: Проверяет данные и создает организацию.
4. Система создает первую учетную запись.
   - Система: Связывает ее с организацией и подтверждает успешную регистрацию.

##### Критерии приемки:
- Без обязательных данных регистрация не завершается.
- После успешной регистрации организация существует в системе.
- Первая учетная запись связана с созданной организацией.

##### Исключения и ограничения:
- Сценарий не описывает повторную регистрацию уже существующей организации.
