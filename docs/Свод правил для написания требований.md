### Свод правил для написания требований

---

#### 1. Структура документа

- Использовать иерархию заголовков:
  - ### - Основные разделы или требования (например, US.1, US.2).
  - #### - Подразделы или ключевые функции (например, US.2.1: Элемент интерфейса кликабельный).
  - ##### - Детализирующие элементы (сценарии, бизнес-правила, примеры, критерии приемки).

- Каждое требование (US) должно содержать:
  - Связь с другими задачами.
  - Изображение в формате ![example.png](thumbnail).
  - Контекст и цель.
  - Описание.
  - Подзадачи или ключевые функции.
  - Критерии приемки.
  - Исключения и ограничения.
  - Ссылки на прототипы или примеры (если применимо).

- Для визуального разделения блоков использовать ----.

- Именование различных категорий требований:
  - User Story: US
  - Use Case: UC
  - Business Requirement: BR
  - System Requirement: SR

- Использование разделителей:
  - UC/BR/SR может относиться к US любого уровня. Всегда использовать знак нижнего подчеркивания (`_`):
    - US.1_UC.1
    - US.1.1_BR.1
    - US.1.1.1_SR.1

---

#### 2. Содержание требований

##### 2.1. Контекст и цель
- В начале каждого требования добавлять блок, описывающий бизнес-цель.
- Это помогает понять, зачем внедряется функционал.

Формат, пример:  
Цель: Предоставить пользователям инструмент для анализа данных и улучшения принятия решений.

---

##### 2.2. Описание
- Начинать с ключевого слова Описание:.
- Кратко описывать задачу, ориентируясь на пользователя и его потребности.
- После описания всегда оставлять пустую строку.

---

##### 2.3. Критерии приемки
- Для каждого функционального требования добавлять блок Критерии приемки.
- Условия должны быть четкими, измеримыми и определять успешность выполнения задачи.

Формат, пример:  
Критерии приемки:
- Пользователь может кликнуть на элемент интерфейса и получить доступ к деталям.
- Настройки сохраняются при переходе между страницами.
- Время загрузки интерфейса не превышает 2 секунд.

---

##### 2.4. Исключения и ограничения
- Указывать, что система не должна делать или в каких случаях функционал может не работать.

Формат, пример:  
Исключения и ограничения:
- Если данные отсутствуют, соответствующие элементы интерфейса недоступны для взаимодействия.

---

##### 2.5. Примеры
- Размещать примеры в отдельном блоке с заголовком Примеры:
- Использовать маркированные или нумерованные списки.

Формат, примеры:  
Примеры:
1. Если в системе 5 зеленых индикаторов и 1 красный, отображается предупреждение.
2. При успешном заполнении всех обязательных полей кнопка "Сохранить" становится активной.

---

##### 2.6. Прототипы и примеры
- Если доступны прототипы интерфейса или UX-примеры, добавлять ссылки на них.
- Это помогает разработчикам и дизайнерам быстрее понять задачу.

Формат, примеры:  
Прототипы:
- [Пример прототипа](http://example.com)

---

#### 3. Общие правила оформления

##### 1. Сценарии:
   - Использовать фиксированную структуру:
     - Вложенные списки с четкой иерархией.

Пример формата сценария:  

Сценарий:
1. Пользователь выбирает тип действия:
   - Категория 1:
     - Система: Отображает поля для заполнения.
   - Категория 2:
     - Система: Открывает дополнительный интерфейс.
2. Пользователь заполняет поля:
   - Если данные корректны:
     - Кнопка "Сохранить" становится активной.
   - Если данные некорректны:
     - Появляется сообщение об ошибке.
3. Пользователь нажимает кнопку "Сохранить":
   - Система: Сохраняет данные и отображает подтверждение.

---

##### 2. Списки:
- Для перечислений использовать маркированные списки (`-`).
- Для нумерованных списков использовать стандартный Markdown.

---

##### 3. Ключевые слова:
- Выделять ключевые слова жирным шрифтом.
- Использовать одинаковую терминологию.

---

##### 4. Технические требования:
- Указывать ограничения, например: Максимальное значение: 1000.

---

##### 5. Оформление таблиц:
- Таблицы должны содержать следующие столбцы:
  - Название поля
  - Пояснение
  - Формат
  - Обязательность
- Использовать стандартный синтаксис Markdown для таблиц.

Формат, примеры:

| Название поля       | Пояснение                                      | Формат                       | Обязательность |
|--------------------------|--------------------------------------------------|----------------------------------|--------------------|
| Имя пользователя         | Уникальный идентификатор пользователя            | Текст                           | Да                 |
| Роль пользователя        | Определяет уровень доступа                       | Выпадающий список: Админ, Пользователь | Да                 |
| Статус задачи            | Отображает текущий статус выполнения задачи      | Выпадающий список: Новый, Выполнен | Да                 |

---

#### 4. Пример требования по правилам:

#### US.1: Отображение списка задач

Цель:  
- Обеспечить пользователям удобный инструмент для управления списком задач.

Описание:  
- Пользователь должен иметь возможность видеть список задач, сортировать и фильтровать их.

Критерии приемки:
- Пользователь может отфильтровать задачи по статусу.
- Сортировка работает корректно.
- Время загрузки страницы не превышает 2 секунд.

Исключения и ограничения:
- Если задач нет, отображается сообщение "Нет доступных задач".

Прототипы:
- [Ссылка на макет](http://example.com)

Общие критерии приемки:
- Интерфейс соответствует утвержденному дизайну.
- Время отклика системы соответствует требованиям.
